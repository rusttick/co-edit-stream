# Generalizing Beyond `possible_agile_workflow.md`: A Composable Graph Architecture for Whole-Factory, Whole-Lifecycle Engineering

Purpose: `possible_agile_workflow.md` sketched one shared, live dataset for one control panel's design/build/test lifecycle. This document researches what changes if the scope expands along three axes at once — **depth** (down to a custom ASIC on a custom board in a custom servo driver in a custom robot in a custom machine), **breadth** (electrical, thermal, chemical, mechanical, software/firmware, structural — every engineering discipline touching a factory), and **parties** (the company, every vendor, every contractor, every regulator, for the entire life of the factory) — and proposes how to design the underlying graph so it stays modular, composable, and scalable rather than collapsing into one impossible monolithic schema.

The honest headline first: **this exact ambition is already a live, decade-long, multi-billion-dollar international effort** — it's essentially what "Industry 4.0" and its Asset Administration Shell initiative, and ISO 15926 before it, actually are. Nobody has finished it. But there's a mature, open-source, standards-backed toolset to build on rather than starting from a blank page, and this document maps it.

## Naming the three axes precisely, since they need different solutions

1. **Decomposition depth** — a factory contains lines, which contain machines, which contain sub-assemblies, which contain boards, which contain custom silicon. Any of these can change independently, at a different pace, owned by a different party.
2. **Discipline breadth** — electrical, mechanical, thermal, chemical/process, structural, software/firmware, and now increasingly ML/AI models embedded in equipment. No single schema designed by one team will ever competently model all of these; that's not a resourcing problem, it's a fundamental separation-of-concerns problem.
3. **Party breadth** — the owning company, equipment vendors, systems integrators, contractors, and regulatory bodies, none of whom will accept a schema controlled by one company, none of whom want to (or legally can) expose their full IP into someone else's central database, and all of whom need to assert facts about the *same* physical things.

The reason a single monolithic graph database with one schema doesn't work isn't scale in the "too many rows" sense — it's that **no single authority should own the schema**, because no single authority owns the domains, the depth levels, or the parties. The architecture question is really: how do independently-owned, independently-evolving pieces of a graph interoperate without requiring one owner?

## Precedents, organized by which axis each one actually solves

### Solving depth: recursive composition and universal identity

- **Asset Administration Shell (AAS, IEC 63278)** ⭐ — the Industry 4.0 reference model for exactly this problem. Every physical or logical asset gets a digital "shell" made of **submodels** (technical data, documentation, safety, condition monitoring, etc.), and critically, an asset's shell can **reference other assets' shells** — a machine's AAS references its robots' AAS instances, which reference their servo drivers' AAS instances, which reference their boards', which reference their ASICs'. This is precisely "custom ASIC in custom board in custom servo driver in custom robot in custom machine," already a first-class, standardized composition pattern, not something you'd need to invent.
  - **Eclipse BaSyx** (MIT license, github.com/eclipse-basyx) is a real, open-source, production-used implementation of AAS infrastructure (registries, submodel servers, SDKs in Java/C++/C#) — an actual codebase to build on, not just a spec.
  - The **IDTA Submodel Template Repository** is an open, growing library of standardized submodel *types* (contributed by many companies/consortia) — the "composable modules" the user is describing already have a real, actively-growing public library.
- **IEC 81346** ⭐ — the reference designation system that gives every object (regardless of discipline — mechanical, electrical, hydraulic, process, software) a consistent, hierarchical identifier usable across every tool and every party. This solves the "how do I even refer to the same real-world object from an electrical drawing, a mechanical CAD model, and a maintenance record" problem, which has to be solved before any cross-domain graph is possible at all. It's already the identity scheme several commercial EDA tools (e.g., EPLAN) use — adopting it rather than inventing a new tagging scheme buys immediate interoperability with tools your future users likely already have.
- **ISA-95 / IEC 62264** — gives a standard vocabulary for the *vertical* decomposition levels (Enterprise → Site → Area → Process Cell/Production Unit → Equipment Module → Control Module), useful as the backbone taxonomy for "how far down do we go" without inventing your own leveling scheme.

### Solving breadth: cross-discipline data exchange that already exists

- **AutomationML (IEC 62714)** ⭐ — an open, free, XML-based standard built specifically to exchange factory engineering data *across* electrical planning, mechanical design, kinematics, and PLC control logic between different tools. It's a harmonized combination of **CAEX** (topology/hierarchy — same role IEC 81346 identity plays), **COLLADA** (geometry/kinematics), and **PLCopen XML** (control logic) — i.e., the multi-discipline breadth problem already has a working, standardized, tool-neutral exchange format, actively maintained and cooperating with OPC UA.
- **ISO 15926** — the deepest, most mature *whole-lifecycle, all-disciplines* data integration standard, built for process plants (oil & gas) but conceptually identical to what's being asked here: an RDF/OWL ontology (ISO/TS 15926-8, -12) designed so that many organizations, over an asset's entire life, can integrate data they each generated independently. Its "facade" pattern (ISO 15926-7) — Web-services-based access to *distributed* plant data repositories rather than one central database — is a direct precedent for the federation approach recommended below.
- **Eclipse Capella / Arcadia** ⭐ — an actively maintained, open-source (Eclipse Public License) MBSE tool that already does hierarchical, cross-discipline (system/software/hardware) architecture modeling with a stated goal of "a consistent digital thread across engineering disciplines," extensible for requirements, safety, and collaboration. Worth evaluating directly as a front-end/methodology, not just a reference.

### Solving party breadth: no single owner, conflicting/partial information, everyone can assert facts

- **Wikidata's data model** ⭐ — the best-proven precedent on Earth for "many uncoordinated parties continuously edit facts about the same set of real-world things, facts can conflict, and the system stays useful anyway." Every fact (**statement**) carries its own **qualifiers** (context — under what conditions is this true), **references** (provenance — who/what asserts this), and a **rank** (preferred/normal/deprecated, for resolving conflicting claims about the same property). Generalizing the earlier document's per-node WIP/Shared/Published status: at factory scale with external vendors and regulators involved, you don't want one status field, you want **statements-with-provenance**, because a regulator asserting "this safety function meets Category 3" and a vendor asserting "this drive's SIL rating is X" are claims from different authorities about the same node, not edits to a single shared field that only one party can own.
- **NGSI-LD / FIWARE** ⭐ — an open-source (Apache-2.0-family), ETSI-standardized information model and API (property-graph semantics encoded as JSON-LD) explicitly built for federated, real-time "digital twin" data at city/industry scale. Its **Context Broker** (reference implementations: Orion-LD, Scorpio, Stellio — all open source) is a working pattern for "what is true right now, published by many independent systems, queryable/subscribable without a single central database owning everything." This is the live/current-state layer; durable history still wants the event-sourced/versioned graph store described in the prior document.
- **ISO 15926's facade / distributed repository pattern** and the broader **Linked Data** approach (each party publishes their own data, linked by shared URIs/identifiers rather than merged into one store) generalize to: a vendor keeps their servo-driver's detailed design data in their own system, publishes an AAS/NGSI-LD-compatible public submodel describing what your factory's graph needs to know, and your graph *links to* it rather than owns a copy. (Further out, **decentralized identifiers (DIDs)** and **verifiable credentials** are the natural mechanism for a regulator to cryptographically attest "this design meets standard X" as a portable, independently-verifiable fact attached to a node — worth knowing exists, not necessary for a first version.)

### Solving schema composability itself: modules, not one big schema

- **openCAESAR / OML (Ontological Modeling Language)** ⭐ — built at NASA JPL specifically to "transform systems engineering into a rigorous, agile, and data-centric practice" using composable ontology modules. OML's explicit unit types — **Vocabulary**, **Vocabulary Bundle**, **Description**, **Description Bundle** — are a direct, working answer to "how do I let the electrical vocabulary, the thermal vocabulary, and a specific factory's actual description of its equipment compose without one team owning the whole schema." Open source, on GitHub, actively developed.
- **Modular Ontology Design Patterns / the MODL library** — a broader research/practice area (not one tool) for building ontologies as swappable, independently-versioned modules built from documented, reusable patterns, explicitly aimed at letting different teams' modules interoperate without central coordination — the schema-design discipline underlying everything above.
- **AAS submodel templates** (again) are this same idea in Industry-4.0-specific, already-productized form: a template is a published, versioned, reusable schema module anyone can adopt for "safety data," "technical data," "documentation," etc., and extend or ignore per-asset as needed.

## Proposed architecture principles (generalizing the prior document's design)

1. **A federation of graphs, not one graph.** Each party (a discipline team internally, or an external vendor/regulator) owns and publishes their own subgraph — technically, an AAS instance (or NGSI-LD entity set, or OML Description) — and the factory's overall graph is the *linking* of these, not a merge into one database. This is the only version of this architecture that scales to real vendors and regulators, since none of them will accept write access to, or full visibility into, a competitor's or client's central store.
2. **A thin, stable core vocabulary; everything domain-specific is a swappable module.** The core defines only universal relationship types — part-of, connected-to, satisfies, verified-by, supersedes, attests-to — modeled the way OML separates a small Vocabulary layer from Description Bundles. Electrical rules, thermal models, chemical process specs, ASIC pinouts, and safety-function requirements each live in their own versioned module (an AAS submodel template, an OML vocabulary bundle, or an AutomationML role-class library) that plugs into the core rather than being hardcoded into one giant schema. This is what makes "the electrical schematic editor" (the QET web port work) just *one module* among many, not a rewrite of the whole system's foundation.
3. **Composition by reference, recursively, using stable cross-discipline identifiers.** An assembly machine's model references each robot's model, which references each servo driver's, which references each board's, which references each ASIC's — using IEC-81346-style reference designations as the identifiers that stay stable across every discipline's own tooling. Nothing needs to be copied into a parent's document; the graph is edges between independently-versioned nodes, all the way down.
4. **Facts, not fields — every assertion carries its own provenance, scope, and status**, following Wikidata's statement/qualifier/reference/rank model rather than a single mutable field per property. This is the generalization of the prior document's per-node WIP/Shared/Published status once regulators and vendors are first-class parties: a regulator's attestation and a vendor's datasheet claim about the same node are both statements with their own provenance and their own status, not competing writes to one field.
5. **Separate the live/current layer from the durable/versioned layer (CQRS).** A context-broker-style layer (NGSI-LD/FIWARE, or the CRDT-based real-time layer from `possible_web_components.md`) handles "what's happening/being edited right now" across whoever's connected; changes get durably committed as immutable, timestamped events into a versioned graph store (the event-sourcing pattern from `possible_agile_workflow.md`), which is what compliance rule engines, audit trails, and historical "what did this look like when it passed FAT" queries actually run against.
6. **Compliance/standards checks are pluggable modules over the graph, not bespoke code.** Generalizing the ERC/DRC idea: a regulatory body or standards organization could, in principle, publish its own rule module (a vocabulary bundle plus a set of SHACL-style shape constraints, or an AAS "compliance submodel template") that any factory's graph can adopt — making a regulator a *type of module publisher* the architecture already supports, rather than a special case bolted on later.

## Where to actually start (don't design a new schema from scratch)

Concretely, for a first real build rather than a research-scale ambition:

1. **Adopt IEC 81346 for identity** from day one, even in the narrow QET-web-port scope — it costs little now and is the single cheapest way to keep a path open to everything above later.
2. **Model the electrical-schematic domain (the existing QET work) as one AAS-style submodel type / OML vocabulary bundle**, not as the foundation of the whole system. This keeps the narrower, already-scoped work (per `possible_untangling_research.md` and `possible_web_components.md`) fully intact and useful — it becomes the first real, working module in the larger architecture rather than being superseded by it.
3. **Build or adopt a small core ontology** (part-of / connected-to / satisfies / verified-by / supersedes / attests-to) using OML or plain RDF/OWL, and treat AutomationML's CAEX and ISO 15926's OWL ontology as *reference material to mine*, not build from scratch — both already encode a huge amount of hard-won, standards-body-vetted domain modeling for exactly mechanical/electrical/process interoperability.
4. **Prototype the live-collaboration layer with the CRDT stack already researched (Yjs/Hocuspocus)** for the single-team, single-module case first; only reach for a full NGSI-LD context-broker deployment once there's an actual second party (an external vendor or regulator) who needs to publish into the graph without your team owning their data.
5. **Evaluate Eclipse BaSyx and Eclipse Capella directly as codebases**, not just as specs — both are real, licensed-permissively, maintained open-source projects that implement large parts of what's described here, and forking/extending one of them may be far less work than building AAS-compatible infrastructure from zero.

## Honest scale and risk assessment

- **This is not a scoped project — it's a north star.** The organizations behind AAS/Industry 4.0 (a multi-country government- and industry-backed initiative running for over a decade) and ISO 15926 (an ISO standard with dozens of participating organizations, developed over ~20 years) are still maturing exactly this problem at industry scale. A realistic plan treats this document as the *direction* to design increments toward, not a version-one specification.
- **The narrower work already scoped remains the right starting point.** Nothing here invalidates `possible_untangling_research.md`, `possible_web_components.md`, or `possible_agile_workflow.md` — the architecture above is explicitly designed so the electrical-schematic editor is one composable module plugged into a core, meaning the earlier, achievable scope is exactly the right first module to build, not throwaway work.
- **Governance is a harder problem than any of the technology here.** Who ratifies a shared core vocabulary; who arbitrates when a vendor's and a regulator's statements about the same node conflict; who's liable when a published module's compliance check is wrong — these are the actual long-pole problems in every precedent surveyed (Industry 4.0's own governance bodies, ISO's standards process, Wikidata's active community moderation), not schema design. Budget for this as real, ongoing work, not a one-time decision.
- **Federation trades ease-of-query for scalability and autonomy.** A single monolithic graph is much easier to run arbitrary queries and rule checks against than a federation of independently-owned subgraphs linked by reference. This is the correct trade for the stated goal (real multi-party, multi-vendor, multi-regulator adoption) but should be a deliberate, understood cost, not a default assumed away.
